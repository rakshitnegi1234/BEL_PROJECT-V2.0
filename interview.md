
For movie-ID coverage, vector-only retrieval found `26 / 92` expected movie IDs, while the hybrid GraphRAG system found `75 / 92`.

## One-Minute Project Explanation

This is a hybrid GraphRAG movie recommendation and factual query system. The problem is that vector-only RAG handles semantic similarity, but it is weak for exact relationship questions and multi-hop reasoning. So I split retrieval into two paths.

For factual questions, the system uses Neo4j because movies, actors, directors, genres, themes, and awards are naturally graph-shaped. For recommendation-style questions like "movies similar to Movie 0227", it uses Pinecone vector search. The query classifier decides which path to use. For graph queries, the LLM does not generate raw Cypher. It generates a restricted JSON query plan, which is validated and compiled into safe read-only Cypher. For similarity queries, Pinecone returns candidates, then Neo4j enriches them with graph facts like genre and theme overlap before the LLM writes the final answer.

The main result is lower hallucination and better answer completeness compared with vector-only RAG.

## Architecture Decisions

### Why Neo4j?

Neo4j is used because the data is relationship-heavy. The system needs to answer questions like:

- Which movies did a director direct?
- Which movies include a specific actor?
- Which Oscar-winning movies include an actor?
- Which movies connect two people?
- Which movies satisfy director, actor, genre, theme, and award filters together?

These are graph traversal problems. Neo4j gives deterministic answers for these relationship queries.

### Why Pinecone?

Pinecone is used for semantic recommendation queries. If the user asks "movies like Movie 0001" or "same vibe as Inception", exact graph traversal is not enough. The system needs embedding-based similarity over movie summaries.

### Why Gemini Embeddings?

Gemini embeddings convert movie summaries and user queries into vectors. These vectors are stored in Pinecone and used for semantic similarity search.

### Why Mistral?

Mistral is used through the NVIDIA API for:

- Structured entity extraction from PDF text.
- Entity extraction from user queries.
- Query classification.
- Query planning.
- Final natural language answer generation.

### Why Query Routing?

The project separates queries into:

- `graph`: exact facts, filters, counts, lists, relationships, and multi-hop questions.
- `similarity`: "similar to", "movies like", "liked", "same vibe", and "watch next" questions.

This is important because not all recommendation-looking queries are semantic. For example, "Recommend all Christopher Nolan movies with Zendaya" should be graph-based because it asks for exact factual constraints.

### Why Not Direct LLM-Generated Cypher?

The system does not directly execute arbitrary Cypher generated by the LLM. That would be risky because the user prompt could influence database commands.

Instead:

1. The LLM returns a JSON query plan.
2. The code validates labels, properties, operators, relationship types, projections, sorting, and limits.
3. Only supported traversal templates are compiled into Cypher.
4. Neo4j sessions use read access.

This reduces prompt injection risk and keeps database access controlled.

## Data Model

### Nodes

- `Movie(title, year)`
- `Director(name)`
- `Actor(name)`
- `Genre(name)`
- `Theme(name)`
- `Award(name, category)`

### Relationships

- `(Director)-[:DIRECTED]->(Movie)`
- `(Actor)-[:ACTED_IN]->(Movie)`
- `(Movie)-[:BELONGS_TO]->(Genre)`
- `(Movie)-[:EXPLORES]->(Theme)`
- `(Movie)-[:WON]->(Award)`

## Indexing Flow

1. `RunIndexing.js` starts the indexing pipeline.
2. `PdfParse.js` extracts raw text from the movie PDF.
3. `Entity_Extractor.js` batches text and asks Mistral to return structured JSON.
4. `GraphBuilder.js` writes extracted entities into Neo4j using `MERGE`.
5. `Vector.js` creates compact movie summaries.
6. Gemini creates embeddings for those summaries.
7. Pinecone stores the embedding vectors with movie metadata.

## Query Flow

### Graph Query Flow

```text
User query
 -> entity extraction
 -> Neo4j entity resolution
 -> graph classification
 -> restricted JSON query plan
 -> whitelist validation
 -> read-only Cypher
 -> Neo4j result rows
 -> final LLM answer
```

Example:

```text
Which Christopher Nolan movies include Zendaya as an actor?
```

This query should go to Neo4j because it requires exact relationships:

```text
Christopher Nolan -> DIRECTED -> Movie <- ACTED_IN <- Zendaya
```

### Similarity Query Flow

```text
User query
 -> entity extraction
 -> similarity classification
 -> Pinecone vector search
 -> Neo4j candidate enrichment
 -> graph-aware reranking
 -> final LLM answer
```

Example:

```text
Recommend five movies similar to Movie 0227, but keep only Action or Adventure movies that share Technology or Dreams.
```

This starts with vector search, but graph facts are used to make the recommendations more grounded.

## Important Cypher Queries

### Movies Directed By Christopher Nolan

```cypher
MATCH (d:Director {name: $director})-[:DIRECTED]->(m:Movie)
RETURN DISTINCT m.title AS title, m.year AS year
ORDER BY m.year DESC
LIMIT 10
```

### Christopher Nolan Movies That Include Zendaya

```cypher
MATCH (d:Director {name: $director})-[:DIRECTED]->(m:Movie)<-[:ACTED_IN]-(a:Actor {name: $actor})
RETURN DISTINCT m.title AS title, m.year AS year
ORDER BY m.year DESC
LIMIT 10
```

### Movies With Actor And Award

```cypher
MATCH (a:Actor {name: $actor})-[:ACTED_IN]->(m:Movie)-[:WON]->(aw:Award {name: $award, category: $category})
RETURN DISTINCT m.title AS title, m.year AS year
LIMIT 10
```

### Movies With Director, Actor, And Theme

```cypher
MATCH (d:Director {name: $director})-[:DIRECTED]->(m:Movie)<-[:ACTED_IN]-(a:Actor {name: $actor})
MATCH (m)-[:EXPLORES]->(t:Theme)
WHERE t.name IN $themes
RETURN DISTINCT m.title AS title, m.year AS year
LIMIT 10
```

### Shortest Path Between Two People

```cypher
MATCH (a:Actor {name: $actor}),
      (d:Director {name: $director}),
      path = shortestPath((a)-[*..6]-(d))
RETURN [node IN nodes(path) | coalesce(node.name, node.title)] AS pathNodes,
       [rel IN relationships(path) | type(rel)] AS pathRels
```

## Interview Questions And Answers

### 1. What problem does this project solve?

It solves the weakness of vector-only RAG for exact factual and multi-hop movie questions. Vector search is good for semantic similarity, but it can miss complete relationship answers. This project combines Neo4j graph traversal with Pinecone vector search so factual questions and recommendation questions are handled by the right retrieval method.

### 2. What is GraphRAG in this project?

GraphRAG means using graph-structured knowledge as part of retrieval. Instead of retrieving only text chunks, the system retrieves structured facts and relationships from Neo4j, such as actor-to-movie, director-to-movie, movie-to-award, and movie-to-theme relationships.

### 3. Why did you use a graph database?

The movie domain is naturally graph-shaped. Actors, directors, movies, awards, genres, and themes are connected by relationships. Neo4j makes it easy to answer multi-hop questions like "Which Christopher Nolan movies include Zendaya and explore Technology?"

### 4. Why not only use Pinecone?

Pinecone gives approximate semantic similarity. It is useful for "movies like X", but it is not reliable for exact filters or complete list answers. If the user asks for all movies by a director, a graph query is more accurate.

### 5. How does the indexing pipeline work?

The indexing pipeline starts in `RunIndexing.js`. It parses the PDF, extracts movie entities using Mistral, builds the graph in Neo4j, then builds the vector store in Pinecone using Gemini embeddings.

### 6. How are entities extracted from the PDF?

`Entity_Extractor.js` splits the PDF text into movie blocks using dashed separators. It sends batches to Mistral and asks for strict JSON with movie title, year, director, actors, genres, themes, and awards. It retries failed batches and strips markdown fences if the LLM returns JSON inside code blocks.

### 7. Why use `MERGE` in Neo4j?

`MERGE` prevents duplicate nodes and relationships. If the same actor appears in multiple movies, `MERGE` reuses the existing actor node instead of creating a duplicate.

### 8. How does query classification work?

`QueryClassifier.js` uses resolved entity context and an LLM prompt to classify the query as `graph` or `similarity`. It also has a heuristic fallback. Exact factual terms like "directed by", "won", "how many", and "list" are graph queries. Terms like "similar to", "liked", and "same vibe" are similarity queries.

### 9. Why is the word "recommend" not always a similarity query?

Because a query like "Recommend all Christopher Nolan movies with Zendaya" is asking for exact factual filtering. It should go to Neo4j, not Pinecone. Similarity requires intent like "similar to", "liked", "same vibe", or "watch next".

### 10. How do you prevent unsafe Cypher execution?

The LLM does not produce raw Cypher. It produces a restricted JSON query plan. The code validates labels, fields, operators, relationship patterns, sorting, and limits. Then the system compiles the plan into Cypher using known templates and parameterized values.

### 11. How does graph query planning work?

`GraphHander.js` asks the LLM for a query plan made of allowed steps, such as traversal, filter, projection, aggregation, sort, limit, describe, or path. The code then validates each step and builds Cypher from safe templates.

### 12. What happens for "tell me about Movie 0243"?

The graph handler uses a `describe` step. It fetches the movie, director, actors, genres, themes, and awards using optional matches, then sends that structured result to the LLM for a plain-English answer.

### 13. How does similarity search work?

`SimilarityHandler.js` embeds the query or source movie title, searches Pinecone for top candidates, removes the source movie, fetches graph context for candidates from Neo4j, calculates genre and theme overlap, reranks candidates, then asks the LLM to produce the final recommendation list.

### 14. What is graph-aware reranking?

Graph-aware reranking means the vector score is not the only ranking signal. The system also checks how many genres and themes a candidate shares with the source movie. Candidates with stronger graph overlap are ranked higher.

### 15. How did you evaluate hallucination?

The project uses RAGAS faithfulness. Hallucination rate is calculated as `1 - faithfulness`. The same 25 questions were evaluated for vector-only RAG and hybrid GraphRAG.

### 16. What were the evaluation results?

Vector-only RAG had `61.00%` faithfulness and `39.00%` hallucination rate. Hybrid GraphRAG had `79.74%` faithfulness and `20.26%` hallucination rate. That is a `48.06%` relative hallucination reduction.

### 17. Why is RAGAS not enough by itself?

RAGAS faithfulness checks whether the answer is supported by context. But for list-style questions, a short incomplete answer can still appear faithful. That is why the project also checks movie-ID coverage to measure answer completeness.

### 18. What was the movie-ID coverage result?

For relationship, multi-hop, and recommendation questions, vector-only retrieved `26 / 92` expected movie IDs. Hybrid GraphRAG retrieved `75 / 92`.

### 19. What are the main hard parts of this project?

The hard parts were:

- Extracting reliable structured JSON from unstructured PDF text.
- Handling LLM JSON formatting errors.
- Routing queries correctly between graph and vector search.
- Preventing arbitrary LLM-generated Cypher execution.
- Evaluating hallucination and completeness separately.

### 20. What bug or weakness would you mention honestly?

One issue is that `RunIndexing.js` points to `./movie.pdf`, but the actual file appears to be under `Data/movie.pdf`. Another issue is that `Vector.js` only indexes `entities.slice(0, 200)`, so if the dataset has more than 200 movies, not all movies enter Pinecone.

### 21. What would you improve next?

I would:

- Fix the PDF path.
- Remove or explain the `slice(0, 200)` limit.
- Add unit tests for query classification and Cypher plan compilation.
- Add Neo4j uniqueness constraints.
- Add stronger filtering for constrained recommendations before the final LLM step.
- Add better observability for query plans, result rows, and evaluation failures.

### 22. How would you explain the project in simple words?

This project is a movie assistant that knows when to use a graph and when to use semantic search. If the question is factual, it uses Neo4j. If the question is about similar movies, it uses Pinecone. This makes the system more accurate than using vector search alone.

## Common Senior Interview Follow-Ups

### What happens if the LLM returns invalid JSON?

For entity extraction, the system retries the batch up to three times. For query planning and classification, it strips markdown fences and tries to parse JSON. Classification has a heuristic fallback, but query planning throws an error if parsing fails.

### What happens if an entity is not found?

`Entity_Resolver.js` puts it in the unresolved list. The classifier and planner receive both resolved and unresolved context. The graph query may fail or return no rows if the needed entity cannot be resolved.

### Why do you use exact database names from resolved entities?

This avoids ambiguity. For example, if the user says "Nolan", entity resolution can map it to "Christopher Nolan", and the query planner can use the exact database value.

### Why use `LIMIT 10`?

It keeps responses concise and prevents very large result sets. The graph handler caps user-provided limits at 10.

### What are possible production risks?

- LLM extraction can miss or incorrectly structure entities.
- Entity resolution using `CONTAINS` may create ambiguous matches.
- The similarity handler relies on LLM final ranking after candidate retrieval.
- There are no automated unit tests for the router or Cypher builder.
- External API rate limits can slow indexing.

### How would you make it more production-ready?

I would add:

- Schema validation for extracted entities.
- Automated tests for query plans.
- Better ambiguity handling in entity resolution.
- Full indexing instead of only first 200 entities.
- Retry/backoff for all external APIs.
- Monitoring for classification errors and empty result rates.
- A web UI or API layer instead of only CLI.

## Short Final Answer For Interview

The core idea is that I did not treat RAG as only vector search. I separated factual graph retrieval from semantic recommendation retrieval. Neo4j handles exact relationships and multi-hop filters, Pinecone handles similarity, and the classifier routes between them. The safest design choice is that the LLM does not execute raw Cypher; it produces a validated query plan that is compiled into read-only Cypher. The measurable result is lower hallucination and better movie-ID coverage compared with vector-only RAG.
